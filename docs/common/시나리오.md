산불 재난 대응 멀티에이전트 시뮬레이터 대표 시나리오 최종본

⸻

0. 공통 환경 설정

공간 구성

* 산맥을 중심으로 양쪽에 A 소방서와 B 소방서를 배치한다.
* 산악지형으로 인해 직선거리와 실제 도로 접근거리가 다를 수 있다.
* 일부 지역은 UAV 접근에는 유리하지만 차량 접근이 어렵다.
* 일부 지역은 강풍 등으로 UAV 접근이 어렵지만 UGV 또는 소방차는 접근 가능할 수 있다.
* 실제 구현 시 실제 산악지형 또는 실제 지형 특성을 단순화한 환경을 사용할 수 있다.

소방서별 보유 자원

A 소방서

* UAV 2대
* UGV 2대
* 소방차 1대

B 소방서

* UAV 2대
* UGV 2대
* 소방차 1대

전체 자원

* UAV 4대
* UGV 4대
* 소방차 2대
* 총 10대

소방차는 단순 출동 자원이 아니라 필요 시 탑재 센서를 통해 현장 관측정보를 제공하는 이동형 센서 자원으로도 사용한다.

이기종 자원 간 임무 대체가 필요한 경우에는 반드시 원래 임무의 요구조건을 다시 확인한다.

UAV가 실패했다고 해서 UGV나 소방차로 즉시 교체하지 않는다.

대체 자원이:

* 원래 임무를 동일하게 수행할 수 있는지
* 일부 목적만 대신할 수 있는지
* 아예 대체할 수 없는지

를 먼저 판단한 뒤 재할당한다.

⸻

시나리오 1. 정기 순찰 UAV의 산불 최초 탐지

목적

외부 신고가 없는 상황에서 UAV가 정기 순찰 중 산불을 스스로 발견하고, 화재 탐지 이후 전체 대응 폐루프가 정상적으로 시작되는지 검증한다.

초기 상황

* 화재 신고 없음
* A·B 소방서의 UAV 중 일부가 사전에 정의된 순찰 경로를 비행
* 나머지 UAV·UGV·소방차는 대기 상태
* 기상조건은 정상 UAV 운용 범위
* 산불은 아직 시스템에 등록되지 않은 상태

발생 이벤트

A 소방서 UAV가 정해진 순찰 경로를 비행하던 중 열화상 또는 영상정보에서 화재 의심 영역을 발견한다.

진행 과정

1. UAV가 정기 순찰 경로를 비행한다.
2. 열화상·영상 등의 센서에서 이상 열원 또는 연기 영역이 탐지된다.
3. UAV가 다음 정보를 시스템에 전송한다.
    * 탐지 위치
    * 탐지 시각
    * 열화상 또는 영상
    * 현재 UAV 위치
    * 센서 상태
4. 총괄 에이전트가 화재 가능성과 위험도를 평가한다.
5. 화재로 판단되면 새로운 화재 대응 Task가 생성된다.
6. Orchestrator가 임무 요구조건을 정의한다.
7. A/B 소방서의 현재 자원 상태를 조회한다.
8. 접근 가능성과 ETA, 센서능력 등을 비교한다.
9. 필요한 경우:
    * 탐지 UAV의 추가 관측
    * 추가 UAV 투입
    * UGV 투입
    * 소방차 출동
        중 적절한 자원을 배치한다.
10. 선택된 자원의 로컬 수행가능성을 확인한다.
11. ACCEPT된 임무는 Safety Layer 검증 후 실행한다.
12. 현장 자원에서 추가 관측값을 수집한다.
13. 산불 확산 모델을 초기화하거나 갱신한다.
14. 예상 확산 방향과 위험지역을 계산한다.
15. 필요하면 추가 자원을 재배치한다.

검증 포인트

* UAV가 정해진 순찰 경로를 정상적으로 수행하는가
* 순찰 중 화재 탐지가 가능한가
* 탐지 이벤트가 Task 생성으로 연결되는가
* 탐지한 UAV와 후속 대응자원을 구분해 운용하는가
* 탐지 → 판단 → 배치 → 관측 → 예측으로 이어지는 기본 폐루프가 동작하는가

기대 결과

외부 신고가 없어도 UAV의 정기 순찰 과정에서 산불을 탐지하고 대응 절차가 자동으로 시작된다.

시나리오 2. 주민 신고 후 소방차·UAV 동시 출동 및 다중 센서 관측

목적

사람의 신고로 시작된 산불 대응에서도 소방차와 UAV가 서로 다른 관측정보를 수집하고, 해당 정보를 환경모델 갱신에 사용할 수 있는지 검증한다.

센서융합이 반드시 예측 정확도를 향상시킨다고 가정하지 않고, 실제 실험 결과를 통해 그 영향을 확인한다.

초기 상황

* UAV 순찰 중 화재 미탐지
* 주민 또는 관제센터에서 화재 신고 접수
* 신고 위치는 A 소방서 관할에 상대적으로 가까움
* A 소방서 소방차와 UAV가 출동 가능한 상태

발생 이벤트

외부 신고가 시스템에 입력된다.

진행 과정

1. 신고 위치를 기준으로 화재 의심 Task를 생성한다.
2. 신고 위치, 지형, 도로 접근성 등을 기준으로 자원을 평가한다.
3. A 소방서 소방차를 현장 대응 자원으로 배치한다.
4. 동시에 UAV를 공중 정찰 자원으로 배치한다.
5. UAV와 소방차는 각각 로컬 수행가능성 또는 운용 가능 상태를 확인한다.
6. Safety 검증 후 임무를 실행한다.
7. 소방차는 이동 중 또는 현장 인근에서 다음과 같은 정보를 수집할 수 있다.
    * 국지 풍속
    * 풍향
    * 온도
    * 습도
    * 연기 관련 정보
    * 가시성
    * 현재 위치
8. UAV는 상공에서 다음 정보를 수집할 수 있다.
    * 열화상
    * 화선 위치
    * 화재 영역
    * 확산 방향
    * 영상정보
9. 서로 다른 관측값을 환경·분석 모듈에 전달한다.
10. 환경 상태 또는 산불 확산 모델을 갱신한다.
11. 초기 예측과 갱신된 예측의 차이를 확인한다.
12. 갱신된 위험지역에 따라 필요 시:

* 추가 UAV
* UGV
* B 소방서 자원
    을 배치한다.

검증 포인트

* 외부 신고가 정상적인 Task 생성 경로로 연결되는가
* 소방차가 단순 출동자원이 아니라 이동형 센서노드로 동작하는가
* UAV와 소방차가 서로 다른 관측정보를 제공하는가
* 관측정보가 실제 환경모델 갱신에 사용되는가
* 갱신된 예측이 후속 자원배치에 영향을 주는가

기대 결과

신고 이후 소방차와 UAV가 각각 현장 관측정보를 제공하고, 해당 정보가 산불 상태 추정과 후속 자원배치 판단에 활용된다.

※ 다중 센서 사용에 따른 예측 성능 개선 여부는 실험 결과로 판단한다.

시나리오 3. A 소방서 UAV 강풍 실패 후 이기종 자원 재평가

목적

직선거리상 가까운 자원이 항상 최적 자원이 아니라는 것을 검증하고, UAV가 임무를 수행하지 못했을 때 다른 자원이 원래 Task Requirement를 충족하는지 다시 평가하여 적절한 자원을 선택하는지 확인한다.

초기 상황

* 화재는 A 소방서와 직선거리상 가까움
* 초기 후보로 A 소방서 UAV가 선택됨
* 산맥 주변에 강한 바람이 발생
* A 소방서에서 화재지역으로 지상 이동하려면 산맥을 크게 우회해야 함
* B 소방서에서는 직선거리는 더 멀지만 도로경로가 더 짧을 수 있음

발생 이벤트

A 소방서 UAV가 현재 풍속이 운용한계를 초과했다고 판단한다.

예:

REJECT: HIGH_WIND

진행 과정

1. 화재 대응 Task가 생성된다.
2. A 소방서가 직선거리상 가까워 A-UAV가 초기 후보가 된다.
3. UAV가 현재 풍속과 자신의 운용한계를 비교한다.
4. 임무 수행이 불가능하다고 판단한다.
5. REJECT(HIGH_WIND)를 반환한다.
6. Orchestrator가 기존 배정을 취소한다.
7. 원래 Task Requirement를 다시 확인한다.

예:

원래 임무가:

* 화재지점 현장정보 수집

이라면 UGV 또는 소방차가 일부 또는 전체 대체 가능할 수 있다.

반대로:

* 상공 열화상으로 넓은 화선 전체 관측

이라면 UGV나 소방차가 동일 임무를 직접 대체하지 못할 수 있다.

8. 대체 가능한 자원만 후보로 다시 선정한다.
9. A-UGV와 B-UGV가 후보라면 실제 도로경로와 ETA를 계산한다.
10. A-UGV는 산맥 우회로 인해 ETA가 길어진다.
11. B-UGV가 실제 도로 기준으로 더 빠르면 B-UGV를 선택한다.
12. 선택된 B-UGV의 로컬 수행가능성을 확인한다.
13. ACCEPT 시 Safety 검증 후 임무를 실행한다.
14. B-UGV가 접근 가능한 지점에서 현장정보를 수집한다.
15. 해당 관측값을 환경모델에 반영한다.

검증 포인트

* HIGH_WIND가 Hard Constraint로 작동하는가
* REJECT가 정상적인 재평가 Trigger가 되는가
* 이기종 자원 대체 전 Task Requirement를 다시 확인하는가
* 직선거리보다 실제 도로경로와 ETA를 고려하는가
* 다른 소방서 자원도 후보로 고려되는가
* 부분 대체와 전체 대체를 구분할 수 있는가

기대 결과

총괄은 가장 가까운 자원이 아니라 현재 임무 요구조건을 충족하면서 실제로 접근 가능한 자원을 선택한다.

시나리오 4. 풍향 변화에 따른 산불 확산 예측 변경 및 부분 재배치

목적

기존 계획이 정상적으로 수행 중이더라도 환경상태가 크게 변하면 기존 판단을 다시 평가하고, 필요한 범위만 재계획할 수 있는지 검증한다.

초기 상황

* 산불이 A 소방서 방향의 사면에서 진행 중
* A 소방서 자원이 주로 투입되어 있음
* B 소방서 자원 일부는 대기
* 현재 풍향을 기준으로 기존 배치가 결정되어 있음

발생 이벤트

시간이 지나면서 풍향 또는 풍속이 유의미하게 변한다.

진행 과정

1. 기존 임무를 정상 수행한다.
2. 새로운 기상정보가 환경모델에 입력된다.
3. 산불 확산 방향을 다시 계산한다.
4. 이전에 위험도가 낮았던 B측 지역의 위험도가 상승한다.
5. 기존 판단 당시 사용했던 풍향·풍속 Assumption이 더 이상 유효하지 않은지 확인한다.
6. Assumption이 위반되면 재평가 Trigger를 발생시킨다.
7. Orchestrator가 현재 Task와 자원 배치를 다시 평가한다.
8. 전체 시스템을 바로 초기화하지 않는다.
9. 영향받은 임무만 우선적으로 재평가한다.
10. 일부 UAV·UGV·소방차를 새로운 위험지역으로 이동시킨다.
11. 필요하면 B 소방서 대기자원을 투입한다.
12. 새롭게 투입된 자원에서 추가 관측값을 수집한다.
13. 환경모델을 다시 갱신한다.
14. 상황 변화가 매우 큰 경우 전체 재계획으로 확대한다.

예상 재계획 수준

일반적인 경우:

Level 2 — Partial Reallocation

대규모 확산 또는 전체 임무 우선순위가 바뀌는 경우:

Level 3 — Global Replanning

검증 포인트

* 풍향·풍속 변화가 재계획 Trigger가 되는가
* 기존 Assumption 위반을 감지할 수 있는가
* 모든 자원을 다시 배치하지 않고 필요한 부분만 변경하는가
* 새로운 예측 결과가 실제 자원 이동에 반영되는가
* 필요 시 부분 재계획에서 전체 재계획으로 확대되는가

기대 결과

총괄이 최초 계획을 고정적으로 유지하지 않고 현재 환경조건에 맞춰 필요한 범위에서 판단을 수정한다.

⸻

시나리오 5. 임무 수행 중 UAV 배터리 저하 및 임무 인계

목적

임무 수행 중 자원의 상태가 악화될 경우 전체 임무가 중단되지 않고 다른 적합한 자원으로 임무를 인계할 수 있는지 검증한다.

초기 상황

* UAV가 산불 감시 임무 수행 중
* 다른 UAV와 UGV는 대기 또는 별도 임무 수행
* 현재 감시 Task는 계속 유지되어야 함

발생 이벤트

임무 수행 중 UAV의 배터리가 복귀 안전마진에 가까워진다.

진행 과정

1. UAV가 지속적으로 Battery State를 보고한다.
2. 배터리가 Return Reserve 기준에 접근한다.
3. 로컬 UAV Agent가 현재 임무 지속 가능성을 평가한다.
4. 복귀 여유 부족으로 계속 수행이 어렵다면:
    REJECT(RETURN_MARGIN_INSUFFICIENT)
    를 반환한다.
5. Orchestrator가 기존 Task의 지속 필요성을 확인한다.
6. Task Requirement를 유지한 채 대체 자원을 탐색한다.
7. 우선 동일 Capability를 가진 대기 UAV를 평가한다.
8. 적합한 UAV가 존재하면 감시 임무를 인계한다.
9. 기존 UAV는 안전하게 복귀한다.
10. 대체 UAV는 로컬 수행가능성 및 Safety 검증 후 임무를 이어받는다.
11. 관측 데이터의 시간적 연속성을 확인한다.

확장 조건

대체 UAV 역시 강풍 등으로 접근할 수 없는 경우:

1. 원래 Task Requirement를 다시 확인한다.
2. UGV 또는 소방차가 임무 목적 일부를 수행할 수 있는지 판단한다.
3. 가능한 경우 제한적 대체 Task를 생성한다.
4. 불가능한 경우 새로운 UAV를 기다리거나 다른 관측전략으로 재계획한다.

검증 포인트

* UAV 상태가 임무 중에도 지속적으로 평가되는가
* 배터리가 완전히 소진되기 전에 안전하게 귀환 판단을 하는가
* Task와 Resource가 분리되어 관리되는가
* 동일 임무를 다른 UAV에 인계할 수 있는가
* 이기종 대체 시 Task Requirement를 다시 확인하는가

기대 결과

개별 UAV 이탈이 전체 임무 실패로 이어지지 않고, 가능한 범위에서 관측 임무가 계속 유지된다.

⸻

시나리오 6. 통신 두절에 따른 STALE → OFFLINE 처리 및 재할당

목적

자원이 실제로 고장난 것인지 단순 통신지연인지 즉시 알 수 없는 상황에서도 시스템이 안정적으로 상태를 관리하고 필요한 경우 임무를 재할당할 수 있는지 검증한다.

초기 상황

* UAV 또는 UGV가 정상 임무 수행 중
* 중앙 시스템과 주기적으로 상태정보 및 Heartbeat 교환
* 현재 Task는 수행 중 상태

발생 이벤트

특정 자원의 상태 메시지가 일정 시간 이상 도착하지 않는다.

진행 과정

1. 정상적으로 Heartbeat를 수신한다.
2. 일정 시간 동안 새로운 상태 업데이트가 들어오지 않는다.
3. 즉시 자원 손실로 판단하지 않는다.
4. 해당 자원을 STALE 상태로 변경한다.
5. STALE 상태에서는 중요 신규 임무 할당을 제한한다.
6. 추가 시간 동안 여전히 응답이 없다.
7. timeout 기준을 초과하면:
    * OFFLINE
    * UNAVAILABLE
        상태로 변경한다.
8. 해당 자원이 수행 중이던 Task를 확인한다.
9. Task가 미완료이고 계속 필요하다면 다른 자원 후보를 탐색한다.
10. Task Requirement를 다시 확인한다.
11. 적합한 자원에 새 Decision ID를 부여해 재할당한다.
12. 기존 자원의 통신이 복구되면 즉시 READY 상태로 전환하지 않는다.
13. 다음 정보를 재동기화한다.

* 현재 위치
* 배터리/연료
* 현재 임무
* 센서 상태
* 로컬 Agent 상태

14. 현재 상태가 확인된 뒤 가용 여부를 다시 판단한다.

검증 포인트

* 통신지연과 지속적 통신단절을 구분하는가
* STALE 상태를 별도로 관리하는가
* 불확실한 자원에 중요한 신규 임무를 계속 할당하지 않는가
* 기존 Task가 필요하면 다른 자원에 재할당되는가
* 복귀한 자원을 즉시 READY 처리하지 않고 재동기화하는가
* 중복 임무 수행을 방지하는가

기대 결과

통신 이상이 전체 시스템 장애로 이어지지 않고 정상적인 상태 전이와 재할당 과정으로 처리된다.

⸻

시나리오 7. 두 소방서 자원의 통합 운용과 대규모 확산 대응

목적

각 소방서의 자원을 독립적으로 사용하는 것보다 두 소방서의 자원을 하나의 총괄이 통합적으로 관리할 때 산불 확산 상황에 더 유연하게 대응할 수 있는지 검증한다.

초기 상황

* 초기 화재는 A 소방서 관할지역에서 발생
* A 소방서 자원이 먼저 투입됨
* UAV·UGV·소방차가 각각 관측 및 대응 임무 수행
* 시간이 지나면서 화재 영역이 확대
* A 소방서 자원만으로 모든 Task 수행이 어려워짐

발생 이벤트

환경모델에서 화재가 산맥을 따라 확산하거나 B 소방서 방향으로 넘어갈 위험이 증가한다.

진행 과정

1. A 소방서의 UAV·UGV·소방차가 초기 대응한다.
2. 각 자원에서 관측정보를 수집한다.
3. 환경·산불 모델을 갱신한다.
4. 확산 위험지역이 증가한다.
5. 새로운 Task 또는 기존 Task 우선순위 변화가 발생한다.
6. A 소방서의 현재 자원상태를 평가한다.
7. 다음 정보를 확인한다.
    * 현재 임무 수
    * 자원 활용률
    * 배터리/연료
    * 예상 복귀 가능성
    * 잔여 가용자원
8. 단일 소방서만으로 대응이 충분한지 평가한다.
9. 부족한 경우 B 소방서 자원을 후보에 포함한다.
10. 각 Task별 요구 수행능력을 확인한다.
11. B 소방서의 UAV·UGV·소방차 중 Task Requirement를 충족하는 자원을 찾는다.
12. 산맥·도로·풍향·ETA·현재 상태를 비교한다.
13. 적합한 자원에게 임무를 배치한다.
14. 각 자원은 로컬 수행가능성을 확인한다.
15. ACCEPT된 임무는 Safety 검증 후 실행한다.
16. A/B 양쪽에서 동시에 관측과 대응이 진행된다.
17. 여러 플랫폼의 관측정보를 환경모델에 전달한다.
18. 산불 확산 예측을 다시 갱신한다.
19. 상황 변화에 따라 추가 재배치 또는 전체 재계획을 수행한다.

검증 포인트

* 자원이 소속 소방서에만 묶이지 않고 전체 시스템 자원으로 평가되는가
* 각 소방서의 잔여 대응능력을 고려하는가
* Task Requirement에 따라 서로 다른 플랫폼을 적절히 선택하는가
* 산맥과 도로망 때문에 실제 접근성이 달라지는 상황을 반영하는가
* 여러 자원의 관측정보가 공통 환경상태에 반영되는가
* 상황 악화 시 부분 재배치 또는 전체 재계획이 가능한가

기대 결과

두 소방서의 자원을 통합적으로 활용해 단일 소방서 운영보다 넓은 관측범위와 더 다양한 대응 선택지를 확보한다.

9. 시나리오 전체가 검증하는 최종 폐루프

본 프로젝트가 최종적으로 검증하려는 것은 다음 반복구조이다.

환경 변화 또는 사건 발생
↓
관측
↓
상태 갱신
↓
산불 확산 예측
↓
Task 생성 또는 기존 Task 재평가
↓
Task Requirement 확인
↓
자원 Capability / State 평가
↓
자원 선택
↓
로컬 수행가능성 확인
↓
Safety 검증
↓
실행
↓
현장 데이터·결과 획득
↓
환경모델 갱신
↓
상황 재평가
↓
필요 시 임무 재할당·재계획

따라서 본 프로젝트의 핵심은 특정 시점에서 한 번의 최적 배치를 계산하는 것이 아니다.

환경·자원·관측 상태가 계속 변하는 상황에서 기존 판단을 재평가하고, 필요한 범위에서 임무와 자원을 다시 배치하며, 현장 관측 결과를 다시 환경상태에 반영하는 적응형 오케스트레이션 폐루프를 구현하는 것을 핵심 검증 대상으로 한다.

11. 최종 데모 구성 권장

최종 발표에서는 모든 시나리오를 하나씩 길게 시연할 필요는 없다.

다음 방식이 적절하다.

개별 기능 검증

* 시나리오 1 → 최초 탐지
* 시나리오 3 → REJECT 및 재할당
* 시나리오 5 → 자원 이탈
* 시나리오 6 → 통신 장애

각 기능이 정상 동작했다는 결과와 로그를 제시한다.

통합 데모

시나리오 7을 중심으로:

1. 화재 발생
2. A 소방서 초기 대응
3. 현장 관측
4. 산불 확산
5. 환경상태 변화
6. B 소방서 자원 추가 투입
7. 일부 자원 REJECT 또는 임무 변경
8. 관측정보 환류
9. 예측 갱신
10. 자원 재배치

가 이어지도록 구성한다.

이를 통해 개별 기능이 마지막에는 하나의 통합 오케스트레이션 시스템으로 동작하는 모습을 보여준다.

12. 시나리오 운영 원칙

1. 시나리오는 발표용 이야기만을 위한 문서가 아니다.
2. 각 시나리오는 구현 요구사항과 통합 테스트 케이스 역할을 동시에 한다.
3. 각 담당자는 자신의 파트가 어떤 시나리오에 관여하는지 확인하고 필요한 기능을 구현한다.
4. 시나리오를 위해 별도 임시 로직을 만들기보다 재사용 가능한 공통 기능을 구현한다.
5. 특정 기능이 어떤 시나리오에서도 사용되지 않는다면 우선순위를 낮출 수 있다.
6. 시나리오의 목적은 가능한 모든 예외를 구현하는 것이 아니라 대표적인 환경변화·자원제약·고장·재할당 상황에서 시스템의 적응성을 검증하는 것이다.
7. 센서융합이나 이기종 자원 대체 효과는 사전에 성공을 가정하지 않고 실험 결과로 판단한다.

⸻

13. 최종 원칙

본 시나리오 세트는 다음 질문에 답하기 위해 구성한다.

산악 산불환경에서 UAV·UGV·소방차와 두 개의 대응거점이 존재할 때, 환경과 자원상태가 계속 변화하더라도 총괄 오케스트레이터가 적합한 자원을 선택하고, 실패나 제약이 발생하면 기존 판단을 재평가하며, 현장 관측 결과를 다시 환경상태에 반영하여 대응을 지속할 수 있는가?

따라서 본 프로젝트의 시나리오는 특정 자원의 성능 자체보다,

탐지 → 판단 → 자원배치 → 실행 → 관측 → 환경 갱신 → 재평가 → 재할당

으로 이어지는 전체 폐루프가 실제로 동작하는지를 검증하는 데 목적이 있다.
