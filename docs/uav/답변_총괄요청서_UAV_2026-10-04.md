# 총괄 팀별 요청서 — 드론(UAV) 항목 답변 (2026-10-04)

- 대상 문서: `docs/common/ADAIR_총괄_팀별_요청서.md` §드론(UAV)팀 (갱신 2026-10-01)
- 브랜치: `feat/uav-orch-requests` (기준 `main` `a9e0116`)
- 상세 API: [uav/API_DEFINE.md](../../uav/API_DEFINE.md) 0.2.0
- **호환성**: 필드를 추가만 했습니다. `status` 네 값(STARTED·IN_PROGRESS·COMPLETED·FAILED), `progress.phase`(DONE = 착륙),
  `observation.position`·`sensor_type`·`values` 는 그대로라서 지금 총괄 코드는 수정 없이 동작합니다.
  새 기능을 쓰려면 아래 "총괄 쪽 할 일"이 필요합니다.

## 항목별 결과

| ID | 결과 | 내용 |
|---|---|---|
| UAV-01 | 완료 (이전 커밋) + 시험 | 실행 키(`task_id`=attempt_id), 같은 키·같은 내용 → `duplicate=true`, 다른 내용 → 409 `EXECUTION_ID_CONFLICT`, 파일 영속·재시작 후 조회, `TaskStatus.uav_id`, 관측 위치(lat·lon·alt_m_amsl) 필수 |
| UAV-02 | 완료 | `EvaluateRequest`·`ExecuteRequest` 에 `observe_duration_s`(10~600 s) 추가. `RETURN_MARGIN_INSUFFICIENT` COUNTER 는 복귀 여유 15% 를 지키는 최대 체류를 계산해 `{"observe_duration_s": n}` 만 제안 (그 값으로 재평가하면 ACCEPT). 최소 체류로도 불가능하면 REJECT. `MODERATE_WIND` 는 COUNTER 를 없애고 ACCEPT + `constraints.warnings=["MODERATE_WIND"]`. `DEADLINE_TIGHT` 는 REJECT. **이제 COUNTER 는 실을 수 있는 필드 하나뿐입니다** |
| UAV-03 | 완료 | 평가 응답(ACCEPT)에 `route_id`·`route_version`·`route_hash`·`route`. 경로 = DEM 으로 경로 최고 지형을 구해 순항고도 = max(관측고도, 최고 지형 + 50 m) → 목표에서 관측고도로 하강. 실행 요청에 `route_id`·`route_hash` 를 실으면 그 경로로만 실행하고, 다르면 409 `ROUTE_NOT_FOUND`·`ROUTE_MISMATCH`·`ROUTE_STALE` |
| UAV-04 | 완료 | `remaining_time_s`(시뮬레이션 초). `deadline`(ISO)은 더 이상 보지 않습니다 |
| UAV-05 | 완료 | 관측값에 `value_status`(`SIMULATED`/`NO_DATA`)·`basis` 를 붙였습니다. 312.5℃ 는 mock 자리표시(`MOCK_FIXED_PLACEHOLDER`)로 표시, real 은 기본으로 값을 비웁니다. 기상 센서: **실기체에는 없음**. mock 에서만 `WEATHER` 를 모의값으로 지원 (형식: `wind_ms`, `wind_dir_deg`, `temperature_c`, `humidity_pct` — 지금은 `wind_ms` 만 값) |
| UAV-06 | 완료 (총괄 방침에 맞춤) | **복귀 중에는 재배정하지 않습니다.** 착륙(`phase=DONE`)까지 evaluate 는 `REJECT/BUSY`, execute 는 409 `BUSY`. 총괄의 "착륙·READY 확인 전까지 점유 유지"와 같습니다. `state.returning_task_id` 로 복귀 중인 Task 를 알 수 있습니다. 예전 동작(복귀 중단 후 새 임무)은 `UAV_RETASK_WHILE_RETURNING=1` 로만 켭니다 |
| UAV-07 | 완료 | `measurements: ["THERMAL","WEATHER"]` — 한 방문에 여러 측정, 결과는 `observation.measurements[]` 에 측정별 `measurement_id`. `observation_type` 이 없으면 이동 가능성만 평가·수행 (기상 전용 임무) |
| UAV-08 | 향후 (60 s 체류 유지) | 순찰·스캔 비행은 하지 않았습니다. **카메라: 없음.** 시뮬레이션 기체는 PX4 Gazebo 기본 x500 (`uav/etc/px4-start-kangwon.sh` 가 모델을 지정하지 않음)이고, 이 모델에는 카메라가 없습니다. 따라서 요청서의 52×42 m(H20T 급 가정) 프레임 계산에 대응하는 실제 카메라는 없고, 지금의 90×90 m 임시 모의 관측범위(`ASSUMED_ORBIT_90M_V1`)를 그대로 쓰는 것이 맞습니다. `GET /capabilities` 의 `camera.status=NONE` |
| UAV-09 | 완료 | `POST /uav/{id}/task/{task_id}/abort`. 관측 전이면 `status=FAILED, reason=ABORTED`, 관측 없음, 기지 복귀(`physical_state` RETURNING → LANDED). 관측 뒤면 `ALREADY_RETURNING`/`ALREADY_FINISHED` 로 상태 변경 없음. 재요청은 처음 결과 그대로 |
| UAV-10 | 완료 | `mission_result`(`PENDING`/`OBSERVED`/`NOT_OBSERVED`), `physical_state`(`PREPARING`·`ENROUTE`·`OBSERVING`·`RETURNING`·`LANDED`·`RETURN_FAILED`·`RETASKED`·`UNKNOWN`), `physical_failure_reason`. 규칙: **COMPLETED ⇔ OBSERVED, FAILED ⇔ NOT_OBSERVED**. 관측 뒤에 FAILED 를 보내는 경로는 없습니다 (복귀 실패는 COMPLETED + `physical_state=RETURN_FAILED`). 관측 ID·내용·시각은 이후 바뀌지 않습니다 |

추가: `GET /uav/{id}/capabilities` — 센서 목록·체류 범위·COUNTER 필드·중단·경로·카메라. 총괄의 `resources.capabilities()` 하드코딩 대신 읽을 수 있습니다.

## 동작이 바뀐 점 (총괄 시험에 영향)

- `orchestrator/tests/test_live_uav.py::test_live_ridge_counter_not_executable_holds` (실서버 시험, 기본 건너뜀):
  능선 목표가 이전에는 `COUNTER(observe_duration_s)` 였으나 이제 **`REJECT RETURN_MARGIN_INSUFFICIENT`** 입니다.
  DEM 경로 확인 결과 관측고도 894 m 로 직선 비행하면 경로 중간 최고 지형(약 1,023 m)을 넘지 못해 순항고도를 1,073 m 로 올렸고,
  그만큼 오르내리는 배터리가 늘어 최소 체류 10 s 로도 복귀 여유 15% 를 못 지킵니다 (95% 출발 시 약 6% 남음).
  임무가 보류되는 결과는 같습니다. 시험의 기대값을 `LOCAL_REJECT:RETURN_MARGIN_INSUFFICIENT` 로 바꿔 주세요.
- `orchestrator_v012/tests/test_connected.py` `moderate` 시나리오: v0.1.2 의 `V012_MODERATE_WIND_ACCEPTED` 예외는 더 이상 걸리지 않고
  일반 ACCEPT 로 출동합니다 (출동 결과는 같음, 기록 사유만 다름).
